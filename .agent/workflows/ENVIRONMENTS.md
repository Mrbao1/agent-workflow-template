# Environment and Branch Contract

| Target | Branch | Purpose | Required checks | Deployment |
|---|---|---|---|---|
| Local development | `feature/*`, `fix/*`, `chore/*` | Fast feedback and isolated integration | targeted tests, build where relevant, zero residual process check | never automatic |
| Test | `develop`, `test/*`, `release/*` | Shared integration and acceptance | clean install, integration/e2e, migrations dry-run, security checks | optional; standard for validation only, release when deployment is requested |
| Production | protected `main` | User-facing release | immutable artifact, full release gate, rollback rehearsal, human approval | CD from approved artifact only |

CI validates and records source revision, build run, runner and artifact digest; test CD accepts that immutable artifact and emits an independently reviewed test receipt. Local/test delivery stops here and never invokes the production provider observer. Production CD accepts only the same digest after provider preflight and a human approval over the complete deployment-decision packet. `deliveryctl promote --result failed` persists `rollback_required` and returns nonzero; failure-safe CD then runs rollback/health/receipt steps and still leaves the job failed. Environment-specific commands come from the exact provider/adapter capability selected in the task contract, not from this generic workflow.

Before a production route is called ready, configure the proposed target during clarification with `agentctl.py configure-production-provider --target <file> --source user:<decision>`. The command writes canonical `agent-production-provider-target/v1` JSON into the contract and prints the content digest the human requirement decision must sign; `approve-requirements` derives TASK from the signed contract, so no manual TASK mutation is allowed. Then run a provider-owned, read-only preflight against that exact remote repository and deployment environments. Its receipt must be no more than 300 seconds old and bind repository/default branch, effective protection/reviews, force-push/deletion restrictions, test/production environment identities, production reviewers, exact artifact source revision, its verified head/merge-commit reachability, and successful required check runs for that same SHA with provider IDs/URLs/evidence digests. Store it only below `.agent/state/evidence/provider-preflight/` and verify it through `agent_control.provider_preflight_observer.signed_adapter`; this adapter is an independent OS-protected host trust root, not `platform_observer`, a caller script or a generic interpreter.

The state path is `awaiting_test → awaiting_provider_preflight → awaiting_production_approval → ready_to_promote`. `approve-production` commits a content-addressed packet over artifact/revision, repository/default branch/production environment, provider receipt SHA and test-summary SHA. Both approval and promotion rerun provider verification and freshness checks, so receipt or candidate drift fails before state mutation. If provider access/adapter is unavailable, the route remains `waiting_human`; if a control is missing, remediate it at the provider and rerun the preflight. Do not silently create or weaken remote policy.

Migration v26 is lossless and fail-closed. Old production `awaiting_production_approval`/`ready_to_promote` return to provider preflight, with approved legacy state archived when present. Old `promoted`, `rollback_required` and `rolled_back` become read-only `legacy_*` history with `assurance=legacy`; they cannot re-enter `promote` or be projected into a new Node8 release receipt.

The repository contains opt-in CI/CD templates, not an active provider configuration. Installing the workflow never initializes Git, creates branches/secrets, enables a provider, configures branch protection/environment reviewers or deploys a product.

An adapter registry entry marked implemented means its local receipt protocol and runner exist; it is not a host-capability attestation. Docker daemon access, Xcode, simulator/runtime availability, browser support, device hardware, provider credentials and remote policy are unverified until the selected execution profile passes its current preflight. Missing hardware, tools, credentials or provider adapters block the corresponding route; documentation and template presence never convert them into verified capabilities.
