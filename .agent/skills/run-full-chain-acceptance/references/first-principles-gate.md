# 第一性原理验收门

## 节点 7 前置条件

- 节点 1–6 已放行，需求、交付项、方案、测试和受测版本可追溯。
- 所有关键事实有来源，没有未确认的 AI 业务推断。
- 每个交付项至少有正常场景，并覆盖适用的异常、边界、恢复、幂等、权限、安全、性能、兼容、数据和回归场景。
- 版本已冻结：优先记录 commit；无 Git 时记录受测文件及 SHA-256。
- 运行环境可重建；用户要求 Docker 时不能用宿主机开发服务代替。
- 实现者、对抗审查者、交叉审查者身份分离。
- 已定义 P0–P3、必测项、打回节点和最终人工决定人。

## 第一性原理重拆

验收前不看实现细节，先从用户目标推导：

1. 用户是谁，真正要完成什么决定或动作？
2. 哪些状态必须永远成立？
3. 数据从哪里进入，经过哪些变换，谁拥有修改优先权？
4. 哪些状态转换可逆、幂等、可恢复？
5. 错误、重复、并发、中断、刷新、过期和恶意输入会怎样？
6. UI、API、存储、计算和日志分别应观察到什么？
7. 哪个反例一旦成立就说明方案本身错误？

先写预期值和不变量，再运行产品，避免用现状改写验收标准。

## 可重放证据

- 版本：commit 或文件指纹、镜像 ID/digest。
- 环境：OS、架构、依赖、浏览器、viewport、Compose 展开配置。
- 命令：完整命令、时间、退出码、原始输出。
- 容器：构建、服务状态、健康检查、端口探测、错误日志。
- 浏览器/API：trace、关键 DOM/API 断言、控制台、失败请求。
- 数据流：输入、处理结果、用户修改、确认值、持久化状态、刷新恢复、派生值。
- 追溯：Requirement ID ↔ Case ID ↔ evidence path/hash。

截图只能辅助。独立审查者必须从需求重新推导关键用例，并校验原始证据、哈希与唯一 integrator 收据；不得重跑已经由该收据证明的全链路。只有发现未覆盖风险时，审查者才可新增不超过三条定向用例，并由 integrator 在同一个正式 run 中执行。

## 放行条件

- 需求—交付项—场景—证据追溯率 100%。
- 所有必测场景通过；Failed=0、Blocked=0。
- P0/P1/P2 功能或数据问题为 0；P3 只能由人明确接受。
- UI、API、存储、计算和日志相互一致，无静默默认值或范围外行为。
- 对抗审查和交叉审查由不同的非实现者完成。
- 最近改动后的受影响链路与核心 smoke 已重跑。
- 恰好一次由 integrator 独占的 fresh-state 全链路通过；对抗与交叉审查独立验证同一收据和各自的定向证据，没有新缺陷。
- 干净环境可复现，清理和回滚可执行。
- AI 只能输出 `release` 或 `do_not_release` 建议；最终由人批准。

## 根因打回

| 根因 | 节点 |
|---|---|
| 目标、需求或成功标准 | 1–3 |
| 数据流、架构、接口或拆分 | 4 |
| 场景或预言值遗漏 | 5 |
| 实现与集成 | 6 |
| 部署、容器与回滚 | 8 或 4 |

禁止在节点 7 只补一段“已通过”文字掩盖根因。
